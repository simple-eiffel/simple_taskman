## QPC across sleep (2026-10-06, Larry slept the machine)
  taskman_cli clockwatch --seconds 300, started 11:36:17, ended 11:41:18:
    gap: both advanced 275.0 s together -> the monotonic counter KEPT COUNTING (sleep is a discontinuity)
    gap: both advanced 6.6 s together -> the monotonic counter KEPT COUNTING (sleep is a discontinuity)
    watched 300 s of monotonic time; jumps or gaps: 2
  System log for the same window:
    Kernel-Power 42  11:36:31  entering sleep (Application API)
    Kernel-Power 130/131 firmware S3 times (a real S3 standby, not modern standby)
    Power-Troubleshooter 1  Sleep Time 15:36:30.17Z  Wake Time 15:41:14.82Z  Wake Source: Power Button
    Kernel-General 1  system time corrected +273,801 ms from the hardware clock at resume
  300 s of monotonic time took 301 s of wall time across about 285 s of sleep,
  so QueryPerformanceCounter advanced through S3 on this build.
  Consequence: the addendum's main branch holds. A sleep arrives as a monotonic
  gap (> Gap_factor x nominal) and TM_SAMPLER emits a discontinuity frame
  (A-110); no rate spans the sleep. No code change needed.
  Note: at resume Windows briefly holds the pre-sleep wall time, then steps it
  forward. Clockwatch did not observe the stale window. If a sample ever lands
  in it, the continuous timeline absorbs it (the offset grows, then shrinks back to 0),
  and that frame is flagged as clock-adjusted. Two earlier attempts (11:21, 11:24)
  did not sleep the machine (no Kernel-Power events) and are not counted.

## CPU tile decision (2026-10-06)
  Larry: "use Processor Utility like Task Manager". TM_APP.Cpu_headline is now
  {TM_METRICS}.Cpu_utility_pct (PDH "\Processor Information(_Total)\% Processor Utility",
  NOCAP100, metric range 0-400%). The value is shown as measured, so under turbo it can read above
  100%, where Task Manager stops at 100. cpu.busy_pct is still sampled, recorded and printed by the CLI.
  ec.sh release -target taskman: 0 problems. Live 15 s run: 14 frames, 0 dropped, sample 8-9 ms.
  Side observation: right after the S3 wake, C: read 100% busy for a few minutes with almost no
  process file I/O; minutes later PDH (both our query and a replica of its calls) read 0.6-3.4%.
  Most likely real post-resume paging/prefetch activity; not reproducible, no code change.
